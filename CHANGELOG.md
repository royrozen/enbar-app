# Changelog

## [Unreleased]
- **Production database sync — the maintenance module reaches prod (2026-09-16).** Found via a live error on `/manager/settings`: the עובדים tab showed "הטעינה נכשלה" because its query selects `employees.maintenance_access_enabled`, a column that existed only in dev. Root cause: all 17 maintenance-module migrations had been applied to `enbar-Webapp-dev` only, while `main` auto-deploys to `enbar-reports.vercel.app`, which runs against `enbar-Webapp-prod`. Prod was missing all 10 maintenance tables, all 6 functions, `profiles.employee_id`, `profiles.display_name` (an older `profile_display_name` migration that had never reached prod either) and both storage buckets — so every maintenance screen, and the QR checklist route, was broken there. Synced by replaying dev's schema migrations in their original order, **skipping** the two data-import migrations (superseded by dev's current data) and **hand-writing** the `platform_admin` policy widening against prod's own 40 policies rather than replaying dev's, since the two databases were built by different migration histories (`prod_align_*` vs dev's own). Machines, periods, tasks and parts were copied at their current values — including the machine and two tasks added on 2026-09-16 — preserving every UUID, `machine_no` and `part_no`, so the two databases now match row-for-row and a QR code resolves to the same machine in both. Prod's column signatures for all 12 affected tables are now identical to dev's. All three machine #001 parts turned out to be test data and were then deleted from both databases, along with their photos' rows — so both now hold the same 40 imported parts and machine #001 has none. (Three orphaned image files remain in dev's `machine-parts` bucket; Supabase blocks deleting storage rows via SQL, and nothing references them.)
Maintenance module (machine × maintenance-period tracking, QR-triggered checklists, parts catalog, fault reporting) — in progress, merged to `main` one phase at a time. Phases 1-5 (+ revisions) done and approved; Phases 6-8 remain.
- **Phase 6 — field checklist flow (branch `feat/maintenance-checklist-flow`).** New `/maintenance/:machineId` route (`src/pages/Maintenance.jsx`): machine header, the machine's periods whose `next_due_date` falls in the current calendar week (Sunday-Friday) grouped by period name with its due date, a task checkbox per `machine_period_tasks` row, and an always-visible `דיווח תקלה / שבר` link (its destination route arrives in Phase 7). No worker/name picker anywhere — `maintenance_visits.profile_id` comes from the session. Submitting writes one `maintenance_visits` row plus, per due period, a `machine_period_logs` row (`fully_completed` true only when every task in that period is checked) and one `machine_period_log_tasks` row per task; only fully-completed periods advance their `next_due_date`. Two functions added this phase, both SECURITY DEFINER and both narrower than the RLS alternative: `advance_machine_period(p_log_id)`, because `machine_periods` UPDATE is manager-only, so a worker otherwise cannot roll a period forward (it acts only on a log row the caller's own visit produced, and only when that log is already `fully_completed`); and `machine_week_checked_tasks(machine_id, week_start, week_end)`, because the per-row SELECT policies are own-visit-only, so a task checked by one worker would have been invisible to the next — it returns just the task ids already checked this week and when, gated on the same `maintenance_access()` predicate the insert policies use. A task already checked off this week renders checked, locked, and dated, so reopening the machine shows real recorded progress rather than a blank list (an earlier localStorage draft of unsubmitted checkbox state was built and then removed in favour of this — only submitted work persists). **Machine QR codes now encode `https://<host>/maintenance/<uuid>` instead of the bare UUID** — a phone camera scanning a bare UUID gets plain text with nothing to open, and there is no in-app scanner, so the module's only field entry point could not actually work. The PRD's §9 guardrail ("`machine_no` is never used in a QR URL") already presumed a URL payload. Both QR call sites build it through `machineQrUrl()` (new `src/lib/urls.js`) so they can't drift; the host comes from `APP_BASE_URL`, which falls back to the production domain rather than `window.location.origin`, since printing from localhost or a preview URL would otherwise produce permanently dead stickers. Error correction raised to `H` (30% recovery) for stickers that live on oily, scratched machines — measured at 49×49 modules, ~1.3mm per module at the 240px print size — and the print sheet now shows the encoded URL in small text so a wrong host is caught before a print run. **Nothing has been printed yet; see TODO.md — changing the host later invalidates every sticker already glued to a machine.** Also fixed two things found along the way: `RequireProfile` now passes the intercepted path to `Login`, which returns there after OTP instead of always landing on the role's default home (the acceptance criterion for a scanned QR on a signed-out phone); and the Sunday-Friday week range is built from local date parts rather than `toISOString()`, which put an evening visit on the previous UTC day.
- **Phase 5 — factory_worker self-provisioning + access-check helper (branch `feat/factory-worker-self-provisioning`, merged to `main`; real-OTP login since confirmed end to end — a first login as an eligible employee created the `profiles` row with the right role, employee link and display name).** On first login, if a session has no `profiles` row yet, the app now attempts to create one itself (`provisionFactoryWorker()` in `src/lib/auth.js`) under the user's own ordinary session — no server function, no admin step, no new secret. A new `resolve_own_employee()` SECURITY DEFINER function (added this phase, since `employees` is otherwise manager-only SELECT) resolves strictly the caller's own JWT phone against an active/access-enabled employee; the actual gate is still Phase 1's `factory_worker self-provision` RLS INSERT policy on `profiles`, unchanged. A rejected insert (unmatched phone, or `maintenance_access_enabled=false`) falls through to the existing "no access" error message rather than a new one. Also adds `src/lib/maintenanceAccess.js`'s `getModuleAccess()`, a small live (never cached) access-check helper for Phase 6/7 to call, reusing the existing `employee_access_match()` RPC. Verified directly against the dev DB: the exact client insert shape succeeds for an eligible employee and is rejected (RLS violation) for both an unmatched phone and a matched-but-disabled one; the live re-check flips access on/off within the same session with no caching. Not verified: an actual phone-OTP login click-through — an agent session can't receive real SMS, so this needs Roy to run it once against the one real employee phone set up for this test.
- **Phase 3-revision — anchor date picker (branch `fix/period-anchor-datepicker`, merged to `main`).** Corrected the yearly/triannual schedule-anchor UI shipped in Phase 3: the two unlabeled number inputs (day, month) read as a duplicate-field bug in the live app. Replaced with a single native date input (`ANCHOR_PICKER_YEAR = 2024`, a leap year, used only so Feb 29 is always selectable in the picker — the displayed year is discarded on every read, never stored). `machine_periods.anchor_day`'s CHECK loosened from 1-28 to 1-31 (the 1-28 range was copied from monthly's day-alone logic, which doesn't apply once day+month are picked together as a real calendar date) — `day_of_month`'s own 1-28 CHECK (monthly) is untouched. Added a February-29-in-a-non-leap-year shift to `compute_next_due_date`'s triannual/yearly branches (→ March 1), checked before the existing Saturday-shift, since `make_date()` throws for Feb 29 in a non-leap year. Verified via direct SQL calls (leap/non-leap/normal cases) and a live add-period click-through in both the mobile and desktop UI.
- **תחזוקת מכונות desktop layout + follow-ups (branch `fix/settings-desktop-layout`, merged to `main`).** Rebuilt the desktop (`lg:` / ≥1024px) layout of the Phase 3/4 machine-maintenance screen as a two-pane split console — machine roster on one side, full detail for the selected machine always visible on the other — replacing an initial 2-column card-grid concept that was rejected on review. Mobile layout/behavior unchanged (verified pixel-identical via screenshot diff). Along with the layout: tapping a part now expands full details inline (price, purchase date, supplier phone/SKU, larger photo — previously only visible via the edit form); the QR block was replaced with a small icon button (between edit and the active-toggle) that opens a print-ready popup (Enbar logo, machine number/name, QR) and auto-invokes the browser print dialog, instead of an always-rendered inline canvas; added a machine search box (name/number/location) above the list, reusing the existing `ManagerDashboard` search pattern. Also fixed a CSS specificity bug in `src/index.css`: `.manager-desktop .input`'s padding shorthand was overriding `select.input`'s reserved `padding-left`, letting the custom dropdown chevron overlap the last word in narrow selects (e.g. "הוספת מחזור טיפול") — distinct from the earlier Safari-only appearance:none bug below.
- **Phase 4 — parts catalog.** Added a `חלקים` tab to each machine's detail view: list/add/edit/deactivate covering all fields (store, price, purchase date, shelf location, descriptive quantity, photo). - **Phase 1 — schema + role model.** 11 new tables (`maintenance_periods`, `maintenance_tasks`, `machines`, `machine_periods`, `machine_period_tasks`, `maintenance_visits`, `machine_period_logs`, `machine_period_log_tasks`, `machine_parts`, `fault_reports`, `fault_report_parts`), all RLS `authenticated`-only. `profiles.role` extended with `factory_worker`/`platform_admin`; `profiles.employee_id` added; `employees.maintenance_access_enabled` added.
